<h2>开动之前，先拿到四样东西</h2>
<p>四个可用地址、掩码与网关、分配的地址属性（是否住宅、归属地）、以及服务商的限制说明（哪些端口封了、是否允许自建服务）。四样齐了再动手，缺一样都可能卡在半路。</p>
<p>第四样最容易被忽略。配置全对但服务连不上，最后发现是端口被封，这种问题白折腾半天。</p>

<h2>第一步：核对地址与参数</h2>
<p>把四个地址、掩码、网关逐项对照订单。特别注意「可用地址数」——段里可能有一两个有特殊用途，实际能用的小于四个。</p>
<p>核对完记下来，写成一张小表。后面配置与验证都对着这张表走，比凭记忆可靠。</p>

<h2>第二步：绑定地址</h2>
<p>绑在网关或绑在服务器，取决于你的结构。如果多台设备要分别用不同地址，绑在网关统一分流更好管；如果只有一台服务器要用四个地址，直接绑在网卡上更直观。</p>
<p>绑定后先在本地测一次：地址是否能通、能否 ping 通网关。这一步不通，后面的配置没有意义。</p>

<h2>第三步：配置回程路由</h2>
<p>这是最容易漏的一步。地址绑上了，但系统不知道怎么把回包送出去，表现是「能发不能收」。要为每个地址配置对应的路由规则。</p>
<p>配完之后逐个测：从这个地址访问外部，看是否能正常返回。四个地址分别测，因为路由规则可能只对其中一个生效。</p>

<h2>第四步：按来源分流</h2>
<p>决定「谁走哪个地址」。最常用的是按来源网段或来源地址绑定，让每组设备固定走一条。规则要写在独立的表里，不要与主路由表混在一起。</p>
<p>规则顺序按「越具体越靠前」排列。通用规则写前面会把特例吞掉，这是最常见的逻辑错误。</p>

<h2>第五步：逐地址验证</h2>
<p>从每个使用方分别发起一次访问，查对方看到的源地址。四组数据全部对上，才算配置完成。</p>
<p>验证时换两个不同的目标站点。某些站点会缓存连接，同一目标重复测可能拿到旧结果。</p>

<h2>三条排错路径</h2>
<p>路径一：地址不通。查绑定是否生效、网卡是否启用、地址与掩码是否配对。<strong>路径二：能发不能收。</strong>查回程路由，这是最典型的原因。<strong>路径三：出口不对。</strong>查策略规则顺序与程序是否指定了源地址。</p>
<p>三条路径覆盖了绝大多数问题。按顺序查，比一遍遍重启设备有效。</p>

<h2>配完之后的收尾</h2>
<p>把「哪个地址归谁用」写成表，归档。这一步看着琐碎，但它是后续所有排查与变更的依据。没有这张表，四个地址很快就会变成「都知道有，没人说得清谁在用」。</p>
<p>另外建议定期复验一次。网络环境会变，配置也可能被别人改动，定期确认比出事再查省力。</p>

<h2>配置完先别急着交付，做一次「拔线演练」</h2>
<p>四个地址配好、验证通过，很多人就直接投入使用了。建议再加一步：人为让其中一个地址不可用（临时下线或改规则屏蔽），观察受影响的设备是否能正常切换到其他地址，以及切换后服务是否继续可用。</p>
<p>这一步能暴露两类问题。一是切换机制根本没配，出故障时不会自动切；二是切换会波及不该受影响的组，说明分流规则写得不够细。两类问题在平时都看不出来，只有演练时才现形。</p>
<h2>常见问答</h2>
<h3>四个地址都要配吗？</h3>
<p><strong>答：</strong>不一定。用不上的可以先不绑，但要知道它们在哪、归谁。</p>
<h3>绑在路由器还是服务器上？</h3>
<p><strong>答：</strong>多设备分流绑路由器，单服务器使用绑网卡。按实际结构选。</p>
<h3>配好后地址还能改吗？</h3>
<p><strong>答：</strong>能，但要同步更新绑定表与策略规则。改了不记录，后面会乱。</p>
<h3>为什么只有一个地址能出网？</h3>
<p><strong>答：</strong>最常见是回程路由没配齐，其次是对应的策略规则没生效。</p>
